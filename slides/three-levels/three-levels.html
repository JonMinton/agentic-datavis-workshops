One chart, three levels of abstraction

The same penguin chart, described as a picture of mappings, as a language-free specification, and as code. Three ways to lay it out on a slide.

OPTION A

Rail and window

Three or four nodes stacked on the left, from most human to most machine. One window on the right shows each level in turn; the code level has vertical tabs for R, Python and JavaScript.

OPTION B

Collapsing stack

Full-width bands stacked top to bottom. Each new level opens while the one above folds to a one-line summary. Ends by tracing one design decision through every level.

OPTION C

Fan-out

Mapping and specification at the top; three implementations side by side below. Makes the "one spec, many languages" point in a single frame.

Press → or space to step, ← to go back. Every reveal is a separate click. Data: Palmer penguins; specification taken from specs/penguins-example-2.yml; chart rendered from the ggplot2 code shown.

Intent: what you'd say to a colleague (or a chatbot)

“Are bill length and bill depth related in the penguins data, and does it differ by species?”

Vague on purpose. A chatbot will guess the rest. An agent in a set-up repo turns it into the next level and shows you what it chose, so you can correct it.

Mapping: the grammar of graphics as a drawing

Every chart is a set of mapping rules from columns to visual features, plus the layers that draw them. This is the level where the design decisions live, and you can do it on paper.

Specification: the same mapping, written down precisely


      
No programming language: “colour: species” means the same thing in R, Python or JavaScript. This is the file you hand the agent, and the file you keep.

Low
Code (R)

      

        

        
ggplot(aes(x = bill_length_mm, y = bill_depth_mm, colour = species)) + geom_point() + geom_smooth(method = "lm")

      

    

    

      
Takeaway
One decision

      

        
Adding species → colour is one line at every level, and it turns one downward trend into three upward ones. That's the decision a person should make. The typing is the agent's job.

For Jon · which to use

  
Choosing a layout

  

    
OptionStrengthsWeaknessesBest for

    
A · Rail and windowAlways shows where you are on the ladder; full window for each level; vertical tabs keep the three languages tidy; easy to add a 4th level (Intent).Eight clicks; the levels are never on screen together, so the link between them is told rather than seen.The main explanatory slide in the talk.

    
B · Collapsing stackReads top to bottom as the levels do; the final step traces one design decision through all three; ends on the chart.Only R at the bottom (no room for three languages); animation needs a laptop, not a PDF.The "why the design decision matters" moment, just before the live demo.

    
C · Fan-outThe one-to-many point in a single frame; shows code length growing as you go down; works in a PDF.Code is too small to read on a projector (deliberately: “you don't need to read it”).A closing slide, or a handout.

  

  
Suggestion: A as the explainer (start at Intent, so the non-technical half of the room has a way in), B's final step as the bridge into the live demo, and C as the handout. All three use the same mapping, YAML and code, so changing one changes them all.

  
Built as one HTML file with no dependencies. Print to PDF (add ?print to the URL to get one page per click). Alternatives: reveal.js (fragments, speaker notes, but a dependency) or Quarto revealjs, which fits the rest of the repo.
